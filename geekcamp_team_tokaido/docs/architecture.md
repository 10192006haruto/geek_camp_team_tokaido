# アーキテクチャと担当境界

> 次の実装予定は[レビュー料理抽出MVP仕様](review-dishes-mvp-spec.md)を参照してください。本書は既存のご当地判定・最大5件版の記録であり、レビュー抽出・最大20件版への実装時に更新します。

## 現在の接続

同一Next.jsアプリ内で処理します。別サーバーは導入しません。

```text
UI（範囲・気分・営業中のみ）
 → POST /api/restaurants/search
 → 入力検証 → 候補取得（現在はモック）→ 正規化・半径判定
 → 後藤担当のclassifyCandidates（ご当地料理の根拠）
 → 営業条件 → 距離順・気分の優先 → 最大5件
 → UIは返された結果をそのまま表示
```

他担当の変更理由はレビューで明示します。公開契約変更は共有型・モック・[API仕様](api-contract.md)を同時に更新します。

## 判定との境界

候補型はsrc/server/discovery/types.tsのCandidateRestaurantを使用します。提供と地域性の出典をlocalDishesまたはmenuItemsとして保持します。検索処理はclassifyCandidatesの結果をIDで対応付けます。5件に制限するdiscoverRestaurants系の入口は検索APIでは使いません。営業条件・気分適用前の切り捨てを避けるためです。

現在は架空の確認済み根拠を持つ東京駅周辺9候補（1件は根拠なし）を使用します。実店舗取得や公式メニュー通信をこのAPIから呼びません。将来の実API接続時には費用・帰属・タイムアウト・0件と障害の区別を確認します。

## 状態と競合

条件変更では位置を再取得せず、3条件と既存位置をAPIへ送ります。現在地更新では明示的に位置を再取得します。成功までは前回結果を保持。API結果のメモリキャッシュキーには位置・半径・気分・営業条件・モードを含めます。位置や気分を永続保存しません。

AbortControllerと世代番号で古い応答を破棄します。UIはAPI結果を再フィルター・再ランキングしません。詳細から戻る時の履歴・フォーカス・スクロール復元は既存実装を維持します。

## デモと検証

「デモで試す」の通常モードは固定座標を同じHTTP APIへ送り、判定まで通します。0件・欠損・失敗・遅延などの表示状態デモはフロント専用データで、結合検証とは区別します。通常の現在地検索も現時点ではモックであることを表示します。

検証対象は入力境界・null/0/false・根拠なし・他県料理・0件・中断・並行要求・6件目以降の採用・HTTPエラー・前回結果保持。スマホ実機の位置許可、戻る、フォーカス、動きを減らす設定も別途確認します。
