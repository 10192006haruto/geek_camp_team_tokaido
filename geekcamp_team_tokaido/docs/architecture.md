# アーキテクチャと担当境界

## 現状

アプリルートはリポジトリ内の`geekcamp_team_tokaido/`です。Next.js / React / TypeScriptのApp Router構成で、`src/app/page.tsx`、`layout.tsx`、`globals.css`などの初期テンプレートがあります。`@/*`は`src/*`を参照します。今回追加するのはMarkdownのみです。

以下のファイル・関数名は実装予定の配置案です。別バックエンドサーバーや新しい依存ライブラリは前提にしません。

## 処理と所有者

```text
UI・現在地・条件・結果・詳細（ふら）
  → 検索クライアント（ふら）
  → POST /api/restaurants/search（Yuuto）
  → 入力検証 → 店舗取得・正規化（Yuuto、最初はモック）
  → 候補店舗の判定・ラベリング（後藤）
  → 条件適用・件数制限・レスポンス整形（Yuuto）
  → UIに表示（ふら）
```

## ディレクトリと編集担当

同じNext.jsプロジェクト内で、担当ごとの編集範囲を分けます。
以下は実装予定の構成です。

| パス | 担当 | 責務 |
|---|---|---|
| src/frontend/ | ふら | UI、状態管理、位置情報取得、検索APIクライアント |
| src/backend/ | Yuuto | 入力検証、店舗取得、モック、外部API接続、検索処理 |
| src/discovery/ | 後藤 | 穴場判定、ラベリング、判定設定 |
| src/shared/ | 関係する担当者で共同管理 | API型、候補店舗・判定結果の受け渡し型 |
| src/app/（api/を除く） | ふら | ページ、レイアウト、グローバルCSS |
| src/app/api/ | Yuuto | HTTPの入口、バックエンド処理の呼び出し、レスポンス |
| public/ | ふら | 画像・アイコン等の公開アセット |
| docs/、AGENTS.md、README.md | 共同管理 | 仕様・開発ルール |
| package.json、package-lock.json、各種設定 | 共同管理 | 依存関係・プロジェクト設定 |

src/app/にはページ構成とHTTPの入口を置き、
主な実装は各担当の専用ディレクトリにまとめます。
別のバックエンドサーバーは作りません。

### 担当間の依存ルール

- frontendはsharedの型を参照し、HTTP経由で検索APIを呼びます。
- frontendからbackend・discoveryを直接importしません。
- backendはdiscoveryの公開関数を呼び、候補店舗を渡して判定結果を受け取ります。
- discoveryはfrontend・backendの内部実装に依存しません。
- sharedには型や共通の契約だけを置き、秘密情報・外部API呼び出し・サーバー専用処理を含めません。
- Geminiを利用する場合、外部API接続はYuuto、判定方針・ラベル・根拠の評価は後藤が担当します。受け渡し方法は導入時に合意します。

### 編集ルール

- 原則として自分の担当範囲を編集します。
- 他担当の範囲を変更する必要がある場合は、理由と変更内容をPRで示し、担当者に確認を依頼します。
- API契約はふら・Yuuto、判定の受け渡し契約はYuuto・後藤で確認します。
- 契約変更では共有型・関連モック・API仕様書を同じPRで更新します。担当をまたぐ変更は関係者で調整します。
- 依存関係や共通設定の変更は、事前にチームで共有します。
- この担当分けは運用ルールです。Gitによる編集制限やレビューの強制設定はまだ行いません。

| 配置案 | 責務 |
| --- | --- |
| src/app/page.tsx、layout.tsx | ページ構成・ブランド・メタデータ |
| src/components/restaurants/ | 導入、検索フォーム、パネル、カード、詳細、状態表示 |
| src/lib/client/search-restaurants.ts | 同一オリジンへのfetch、レスポンス確認、エラー変換、キャンセル |
| src/types/restaurants.ts | API共有型のみ。契約は[API仕様](api-contract.md) |
| src/app/api/restaurants/search/route.ts | HTTP・入力検証・ステータス変換。秘密情報を返さない |
| src/server/restaurants/ | 検索処理、取得インターフェース、モック、将来のPlaces実装 |
| src/server/discovery/ | 候補の判定、ラベルと根拠、チェーン・レビュー閾値等の設定 |

サーバー専用処理はClient Componentからimportしません。ブラウザでの位置取得・インタラクション部分をクライアント境界に置きます。UIからPlacesやGeminiを直接呼びません。

## 差し替える境界

過度な抽象化を避け、店舗取得と判定をそれぞれ一つの境界として始めます。

- 店舗取得：`fetchCandidates(request, signal): Promise<CandidateRestaurant[]>`。取得項目を正規化し、値と出典・根拠を保持します。モックと実APIをここで差し替えます。
- 候補型：公開店舗情報の元データに加え、料理や地域性の根拠、出典、取得時点など判定に必要な情報を扱います。具体的な項目はYuutoと後藤で合意します。取得不能な情報を捏造しません。
- 判定：`classifyCandidates(candidates, config): Promise<DiscoveryDecision[]>`。店舗ID、採否、ラベル、理由、参照した根拠を返す案です。判定処理からUIやHTTPレスポンスに依存しません。
- レビュー閾値は未確定の設定値です。チェーン除外や不明値の扱い、並び順も合意後に実装します。レビュー数の少なさを地域性・地元の支持の根拠にしません。
- 検索処理が半径等の条件を適用し、判定結果と統合して最大5件を返します。予算はモックでは明示した円の値で検証し、実APIで価格帯しか得られない場合の扱いは別途決定します。

## 状態と競合

初期・位置取得中・位置取得失敗・検索中・成功・0件・検索失敗を区別します。編集中条件、適用済み条件、結果、選択中店舗、一覧のスクロール位置を保持し、詳細から戻っても復元します。保持方式（共通親状態・履歴等）は実装時に選び、位置情報を不要に永続化しません。

条件の編集やパネルの開閉では結果を消しません。再検索成功時に結果と適用条件を一緒に更新します。失敗時は前回結果と今回の失敗を区別します。

検索クライアントにAbortSignalを渡し、前回のリクエストを中断します。さらに検索IDで最新要求のみ状態へ反映し、中断できなかった応答・エラーも古い要求からは反映しません。位置情報取得のコールバックにも同じ世代管理を適用します。

## モックと実API接続

モックもUIから同じHTTPエンドポイントを経由します。画面から直接モック配列を読みません。店舗名に「架空」を含め、画面でモックであることを示します。固定座標は明示的に選択した開発用操作だけで使います。

成功、少数件、0件、null混在、APIエラー、遅延・応答逆転を再現できる開発用シナリオを用意する予定です。切替方法は未実装で、本番の公開APIに障害注入用パラメータを安易に追加しません。

実API接続前に利用可否、課金、取得フィールド、帰属、保存条件を確認します。店舗取得のアダプターを差し替え、外部データの実行時検証、タイムアウト、制限時の応答、必要な帰属表示を実装します。Google Mapsの地図は将来追加できるよう、店舗座標を契約に含めます。

サーバー専用キーに`NEXT_PUBLIC_`を付けません。将来のブラウザ用Mapsキーはサーバー用と分け、HTTPリファラー・許可API・クォータ等の制限を設定する方針です。具体的な設定方法は導入時の公式情報で確認します。現在キーや環境変数は追加しません。

## 実装後の検証計画

- 入力検証：座標境界、範囲外、半径許可値、予算、nullと省略、型違い、壊れたJSON。
- 契約：0件、returnedCount一致、最大件数、未知と実測0、営業不明とfalse、価格帯と円の区別。
- 判定：根拠のない地域ラベルを付けない、欠損候補や閾値境界。
- HTTP：モックをAPI経由で取得、エラー形式・ステータス、内部情報非露出。
- UI：位置拒否・タイムアウト・取得不能、固定座標表示、条件保持、スクロール復元、APIエラー再試行、遅い要求の無視。
- 操作：導入のセッション制御・スキップ・動きを減らす設定、パネルのフォーカス・Escape、スマホとPC。

検証コマンドは[README](../README.md)を参照してください。現段階でこの計画が実施済みという意味ではありません。
