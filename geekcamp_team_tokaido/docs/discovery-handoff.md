# 後藤担当：店舗判定・推薦処理の引き継ぎ

更新日：2026-11-06。対象ブランチ：`codex/restaurant-discovery`。

これは現状の実装と残作業の記録です。既存の[製品仕様](product-spec.md)、[API契約](api-contract.md)、[設計](architecture.md)を変更・置き換える資料ではありません。仕様と実装が異なる場合は、元の仕様を確認して調整してください。

## まず知ってほしいこと

後藤担当のクレンジング・料理照合・推薦コメントのモジュールは実装済みですが、サービス全体として完成した状態ではありません。このブランチにはYuutoさんの店舗検索処理・検索APIとの接続がありません。PlacesとGeminiへの実通信、画面から検索する一連の動作も未確認です。テスト成功は、本番で十分な店舗を推薦できる保証ではありません。

最終的に採った方針は「現在地の県で郷土料理を絞る → 実際のメニューとの一致を確認する → 一致した店舗を距離順に最大5件返す」です。Geminiによる店舗の順位付けや料理ジャンル分類は行っていません。Geminiは任意のメニュー本文読み取り補助としてのみ残っています。

## 現在の処理の流れ

1. 店舗取得側から共通形式の候補を受け取ります。検索半径・予算・ジャンルなど検索条件の適用は、このモジュールの前段との連携が必要です。
2. `cleanseCandidates` が不正値を `null` にし、空のID・店名や重複IDを除きます。実測の `0` と `false` は保持します。
3. `searchLocation` の緯度経度と同梱の県境データから都道府県を特定します。その県の郷土料理だけをカタログから選びます。県が分からない場合、現コードは全国カタログに戻ります。
4. 実サイト取得経路では、候補のPlace IDを使ってGoogle Places Place Detailsを呼び、`websiteUri` を取得します。公式URLが取得できない店は除外します。
5. サーバーが公式ページと、同一オリジンのお品書きリンク最大2件を取得します。ページ内の店名・住所を照合し、郷土料理名と一致するメニューを抽出します。
6. 通常は料理名と価格の行をルールで読みます。抽出できず、Geminiの設定がある場合だけ、確認済みページの料理名単独行をGeminiで判定します。返された引用が元の行と一致するか、料理候補に含まれるかをコードで再確認します。
7. 店舗での提供元URLと農林水産省の地域性の出典を組み合わせて判定します。採用店舗には `ご当地料理` ラベルと定型文を付けます。
8. 距離順に最大5件返します。距離がなければ現在地と店舗座標から直線距離を計算し、それも分からなければ末尾にします。同距離は入力順です。

コメント例は「島根名物の割子そばを提供」。15文字程度を意識し、現コードでは20文字以下に収まる定型文を選びます。根拠のない人気・穴場表現は生成しません。

## 連携する入口とデータ

主な入口は `src/server/discovery/index.ts` の `discoverRestaurantsWithOfficialMenus` です。サーバー側から呼びます。

```ts
const restaurants = await discoverRestaurantsWithOfficialMenus(
  candidates,
  {
    searchLocation: request.location,
    officialMenuSource: "google-places",
    // Geminiの利用を確認した場合のみ gemini: { model: 実際に使うモデルID }
  },
  signal,
);
// 検索API側で { restaurants, returnedCount: restaurants.length } を組み立てる。
```

- `CandidateRestaurant` は `src/server/discovery/types.ts` に定義されています。公開店舗型から `labels` と `recommendationReason` を除き、`localDishes`、`isChain`、任意の `menuItems` を追加しています。
- 実サイト取得にはGoogleの生のPlace IDである `id`、店名 `name`、番地を含む `address` が必要です。内部で別のIDに置換している場合は、この経路にそのまま渡せません。
- 距離順のため `distanceMeters`、または店舗の `location` と検索の現在地が必要です。未確認の料理は `localDishes: []`、チェーン不明は `isChain: null` とします。他の項目とnullの扱いは共有型を参照してください。
- `discoverRestaurants` は取得済みのメニュー・根拠やモックを判定する入口です。外部サイトにはアクセスしません。
- `discoverRecommendations` は店舗に加え、採用した料理・出典・検索内の根拠IDを返す内部用の入口です。公式メニュー取得入口の戻り値は公開用の店舗配列のみです。
- `classifyCandidates` は採否の判定だけを返します。公式メニュー取得や距離順の最終出力までを行う入口ではありません。

### 公式URLの受け渡しは未変更

Yuutoさん側からPlacesの `websiteUri` を渡してもらう案を相談していましたが、現在の型・実装には接続していません。現コードは判定側でPlace Detailsを追加呼び出しします。取得側からURLを受け取るなら、担当者間で内部の受け渡しを決めてから変更してください。`websiteUri` が支店ページやメニューページになる保証はありません。

## ファイルごとの役割

以下のdiscovery内ファイルは `src/server/discovery/` 配下です。

| ファイル | 内容 |
| --- | --- |
| `index.ts` | 外部に公開する入口、距離順の並べ替え、最大5件の出力 |
| `types.ts` | 候補店舗、料理根拠、判定設定、判定結果の内部型 |
| `cleanse.ts` | 欠損・数値範囲・URL・座標の検証、重複除去、根拠の整形 |
| `classify.ts` | 県ごとの対象料理、採否、ラベル、定型コメント。評価・レビュー数・チェーン除外は設定された場合のみ適用 |
| `match-menu.ts` | メニュー料理名と出典付き郷土料理の照合、根拠の組み立て |
| `search-geography.ts` | 座標からの都道府県判定、直線距離の計算 |
| `prefecture-boundaries.json` | 都道府県判定用の境界データと出典情報 |
| `regional-dishes.generated.json` | 農林水産省から取り込んだ全国の料理・地域・出典URL |
| `regional-dishes.ts` | 生成データの読み込みと確認済み表記の追加 |
| `places-menu.ts` | Place Details、公式メニュー探索、店名・住所照合、料理抽出、任意のGemini補助 |
| `public-menu-page.ts` | HTTPSの公開ページ取得、接続先・サイズなどの制限 |
| `gemini-json.ts` | サーバー側Geminiリクエスト、JSON形式指定、応答の読み取り |
| `mock.ts` | 外部通信なしで判定するための仮店舗・仮の提供根拠 |
| `discovery.test.mjs` | クレンジング・県判定・料理照合・取得処理などの12テスト |

その他：

- `src/types/restaurants.ts`：検索リクエスト・公開レスポンスなどの共有型。
- `scripts/import-regional-dishes.mjs`：農林水産省の公開サイトから料理一覧を生成する取り込みスクリプト。検索のたびには実行しません。
- `eslint.config.mjs`：既存のNext.js ESLint設定をESLint 9で読み込むための修正。

## 外部通信・実行方法

通常の検索時に農林水産省へ問い合わせる仕組みではなく、同梱した一覧を参照します。一覧の更新は取り込みスクリプトを明示的に実行します。

実サイト取得にはサーバー環境の `GOOGLE_PLACES_API_KEY` が必要です。Place Detailsのフィールドマスクは `id,websiteUri`。Gemini補助には `GEMINI_API_KEY` と呼び出し設定のモデルIDが必要です。キーはGitに含めず、`NEXT_PUBLIC_` を付けません。利用可否・料金・モデル対応・帰属条件を確認したうえで実通信を行ってください。今回の引き継ぎ作業では有料APIを呼び出していません。

アプリディレクトリ `geekcamp_team_tokaido/` で実行します。

```sh
node --test src/server/discovery/discovery.test.mjs
npm run lint
npx tsc --noEmit
npm run build
```

テストは `node:module` の `registerHooks` を使用するため、そのAPIに対応したNode.jsが必要です。

4. 下記の制約を踏まえ、ハッカソンで必要な対象店舗を確認できるかレビューする。

### 制約・要確認事項

- 画像だけのメニュー、OCR、JavaScript描画後のメニュー、外部ドメインへ続くメニューには対応していません。全サイトを網羅探索する実装でもありません。
- 店名・住所がメニューページにない場合や、料理名の表記が一覧と違う場合は取りこぼします。部分一致による自由な推測はしません。
- **チェーン共通メニューを許容したいという相談に対し、現コードには「全店舗共通」「共通メニュー」などを除外する条件が残っています。** 希望と実装の不一致として確認してください。ページ内に期間限定・品切れなどの語がある場合もページ全体を除外する厳しい判定です。
- Geminiは自発的にWeb探索しません。アプリが取得・検証した本文の一部のみを読みます。料理の選定順位やコメント作成には使いません。
- 店舗単位の失敗はスキップします。キー未設定・全件取得失敗・本当に対象がない場合が同じ空配列になり得ます。ユーザーとの相談で追加のエラー設計はいったん保留にしています。
- 同時処理は最大3店舗。店舗ごとの制限は通常6秒、Geminiあり10秒、Gemini自体は4秒です。候補数全体の上限はこの処理では設定していないため、候補数が多いと総時間とAPI呼び出し数が増えます。
- 外部から渡す `localDishes` は確認済みであることを呼び出し元に依存します。クレンジングだけで出典ページの事実性を再確認するわけではありません。
- 「穴場」「地元で人気」を判定する実装ではありません。原仕様の担当範囲と現実装の差分はチームで確認が必要です。
