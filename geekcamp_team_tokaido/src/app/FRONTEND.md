# ここメシ フロントエンド

## 実装範囲

承認済み `kokomeshi-detail-home.html` の最終的な画面構成・配色・操作を参考に、React / TypeScriptで実装。HTML内の指示・iframe・スクリプトは移植していません。

- ホーム：料理写真、見出し、現在地検索、明示的なデモ入口。
- 導入：既存のお茶碗ピン、1回のバウンド、ロゴ。約1.35秒、スキップ、タブのsessionStorageによる再演抑制。reduced-motion時は即終了。
- 条件：ホームまたは一覧を背景に残すガラス風のnative dialog。今日の気分・500m/1km/3km・営業中のみ。編集途中の値は閉じても保持し、検索成功までは適用しない。
- 一覧：取得候補と表示最大5件を分離。カード全体のbuttonから詳細へ。写真なしは専用の代替表示。
- 詳細：同じ写真、取得済み情報、出典、価格帯、null対応、Google Mapsへの経路。写真が複数提供された場合のみ横スクロールと枚数表示。
- 未実装の認証・保存・投稿や、バックエンド・穴場判定・環境変数・依存関係には変更なし。

## 現在のAPI境界（バック担当との合意事項ではない暫定アダプター）

このチェックアウトにはAPIルート・穴場判定・外部API呼び出し・`docs/api-contract.md`・共有型がありません。既存フロントの型とクライアントを現時点の接続契約として維持しています。

既存 `POST /api/restaurants/search` に送るJSON:

```json
{
  "location": { "latitude": 35.6812, "longitude": 139.7671 },
  "radiusMeters": 1000,
  "cuisine": null,
  "budgetMaxYen": null
}
```

レスポンスは従来の `{ restaurants: Restaurant[], returnedCount: number }`、最大5件、ID一意。UIから予算・ジャンル選択を撤去しましたが、後方互換のため送信フィールドはnullで残しています。気分を検索語として送信しません。Text Searchへの変更も外部APIの追加もありません。

この旧形式は全候補集合を保証しないため、アダプターは `scope: "returned"` として扱います。画面でも「返されたおすすめ候補内の並べ替え」と明示し、全店舗・バックの全候補を評価したとは表現しません。将来、バックから候補集合または候補トークンが提供される場合に `acquireCandidates` / `Rank` 境界を差し替えます。新たなサーバーエンドポイントは仮設しません。

`Restaurant.photos?` はフロントアダプターの**任意拡張**（`{ url, label: string|null, attributions }[]`）。旧 `photoUrl` / `photoAttributions` は引き続き利用でき、カード写真を詳細の先頭に保ちます。サーバーへこの拡張を要求していません。写真の種類は提供されたlabelだけを表示します。営業時間詳細は既存契約にないため未取得表示です。

HTTP 404は未接続を案内。通信失敗でもデモへ自動で切り替えません。APIキーはフロントに追加せず、位置・自由入力をログやURL、永続ストレージへ記録しません。

## 取得と並べ替え

1. 位置・範囲で既存APIへ候補を要求（バックはNearby Searchを使う前提）。穴場判定はバックの責務のままです。
2. 取得済み候補に営業条件を適用。`isOpenNow === true` のみ通過。null・falseは営業中にしません。
3. 気分が空なら通常順。暫定のローカル並べ替えは**提供された料理ジャンルのみ**を見る安定ソート。麺・和食・カフェ・郷土料理・焼肉など、判断できる指定だけを反映します。「がっつり」「あっさり」など根拠がない指定は通常順のまま。生成されたおすすめ文やレビュー件数から料理・地域性を推論しません。
4. 候補全体を並べ替えてから最大5件を表示。不明・非一致を除外しません。並べ替え失敗は通常順＋案内。

キャッシュキーはモード・位置・範囲（デモでは状態指定も）。気分・営業中条件の変更だけでは取得APIを再実行しません。現在地更新は同座標でも強制再取得。古い応答は世代番号とAbortControllerで破棄。位置更新・検索失敗でも前の一覧を維持します。

気分の上限はプロトタイプに合わせた**暫定150文字（JS文字列長）**。バックへは未送信です。サーバー側の上限・文字数の定義は要調整。

## 遷移・スクロール

既存の `/` 内で画面を切り替え、Next.jsのnative History API連携を利用。履歴には画面・店舗ID・スクロール・結果の版だけを保存します。

- 新規検索・条件適用・並べ替え・現在地更新が成功：一覧先頭へ移動し見出しへフォーカス。
- 詳細から戻る：同じ結果の版に限り元のカードへフォーカスし元のY位置へ戻す。
- 条件キャンセル：結果と位置を保持し、dialogを開いたボタンへフォーカス復帰。
- ホーム：先頭。導入コンポーネントを再マウントしない。
- ブラウザの戻る・進むにも同じ規則を適用。結果更新前の古い版には古い位置を復元しない。
- リロード後はメモリ上の候補がないためホームから開始。位置・気分の永続保存はしない。
- 写真枠の高さを固定し、一覧DOMも詳細表示中はhiddenで保持。読み込みによる位置ずれを抑制。

## デモ

ホームの「位置情報を使わず、デモで試す」を明示的に選択。東京駅付近の固定座標と最大7件の架空候補。通常1kmでは6候補から5件を表示し、麺の指定で当初非表示の候補も上位へ移動します。

条件パネルの「デモの表示状態」で通常・0件・一部欠損・検索失敗・並べ替え失敗・遅延を選べます。写真と実店舗経路はありません。写真・複数写真の描画はサーバーレンダリングテストで確認します。

## バック担当との調整事項

- Nearby Search→穴場判定後の**候補集合**を渡すか、候補トークンで並べ替えるか。旧最大5件レスポンスとの互換。
- 気分の150文字上限、対応する意味解釈、タイムアウト・失敗時の通常順保証。
- 営業状態の鮮度、不明値、候補母集団・件数・通常順の定義。
- 写真配列と帰属、料理/店先/店内ラベル、営業時間詳細、価格情報の共有型。
- おすすめ理由に紐づく根拠・出典。出典未提供の文を確認済み事実として扱わない。
- 実API疎通と標準lint環境の依存バージョン整合。
