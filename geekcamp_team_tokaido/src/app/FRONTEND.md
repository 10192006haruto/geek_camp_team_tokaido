# ここメシ フロントエンド

> 最新の担当分離：Nearby取得・検索APIへの接続はYuuto担当として今回の変更から外しました。ふら側は取得済み最大20候補を受け取るprepareReviewResultsと、最終5件の選定・表示までです。通常検索は旧モックのままです。[現在の担当境界と検証記録](../../docs/review-search-integration-2026-11-07.md)を優先してください。

## 3条件の契約

検索範囲500m/1km/3km（初期1km）、今日の気分（任意・最大150 UTF-16コード単位）、営業中のみ（初期OFF）に統一しました。現在地はユーザー操作後に取得。ジャンル・予算入力はありません。

共有型はsrc/types/restaurants.tsを利用します。フロントのRestaurant.photosは表示用の任意拡張です。

```json
{
  "location": { "latitude": 35.6812, "longitude": 139.7671 },
  "radiusMeters": 1000,
  "mood": "麺が食べたい",
  "openNow": true
}
```

POST /api/restaurants/searchの結果をそのまま表示します。フロントは最大5件と必須のinferredMenuを受理します。検索APIは現在旧モック・最大5件の互換状態で、レビュー抽出への接続はYuuto担当です。条件変更はAPIへ再送し、前回5件だけの並べ替えは行いません。実検索は同一条件でも再取得し、デモのみ候補を再利用します。気分は候補取得の検索語に使いません。

料理名・ジャンルから判定できる気分のみ優先。未対応の気分は距離順で、気分不一致でも除外しません。

## デモ

通常デモは料理名・引用・架空投稿者を持つフロント専用データで表示を確認します。検索API接続とは別です。現在はバックも架空店舗を使うモックです。実API・有料APIは呼びません。普通の現在地検索もモックであることを表示し、東京駅から離れた位置では0件になります。

「デモの表示状態」の0件・欠損・失敗・並べ替え失敗・遅延はフロント内の専用シナリオで、通常デモのHTTP結合確認とは別です。

## 状態・操作

位置情報拒否・タイムアウト・取得不能を区別。検索失敗時は前回結果・入力を保持します。AbortControllerと世代番号で古い応答を破棄。位置・気分をログや永続ストレージに保存しません。

詳細から戻る際のスクロール・カードフォーカス復元、ブラウザ履歴、ダイアログのフォーカス復帰、導入のスキップ・reduced-motion対応は維持しています。

## 検証

アプリルートでnpm run lint、npx tsc --noEmit、npm run buildを実行します。
フロントテストは既存scripts/test.mjs、サーバーはnode --test src/server/restaurants/search.test.mjs src/server/discovery/discovery.test.mjsで実行できます。
ブラウザ実機のフォーカス・位置許可・スクロール・reduced-motionはユニットテストと別に確認が必要です。

## 料理と根拠の表示

カードに料理名、詳細に原文引用・投稿者・元レビューへの安全なリンクを表示します。投稿日時、投稿者画像、翻訳の案内・原文はメタデータが提供された場合に表示します。地域性・現在の提供は断定しません。原文はHTMLとして挿入しません。

APIの504は時間切れ、503は利用不可として案内し、前回結果を保持します。取得側の帰属要件・モデル送信条件は実データ接続前に確認が必要です。

実装・実通信の結果は[検証記録](../../docs/review-dishes-implementation-2026-11-07.md)を参照してください。
